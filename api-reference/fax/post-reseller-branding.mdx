This internal review page records the behavior captured for POST /reseller/branding.

<ParamField header="access_token" type="string" required>API access token.</ParamField>

## Captured contract

```text
Save Reseller Branding API

Endpoint:
POST /api/reseller/branding


Description:
Partial update. Send only sections/fields to change. Omitted fields are left unchanged. Invalid config fields are skipped silently. Nested top-level branding is ignored.




Success data always matches GET shape (configuration + custom_branding).

Case D — Logo upload (multipart)

Request

POST /api/reseller/branding
access_token: {token}
Content-Type: multipart/form-data
configuration[product_name]=Amplify
configuration[provisioning_mode]=client
custom_branding[company_name]=Amplify
custom_branding[accent_color]=#197700
logo=<file>
logo_dark=<file>
Multipart fields logo / logo_dark are top-level (cannot nest files).
Require custom_branding section present so logos attach to that save path.




Response 200 — same GET shape; logo_light_background / logo_dark_background are new presigned URLs.

Case E — Sub-user (sender email only)

Sub-user with permission may send only custom_branding.sender_email_address (mapped to subuser_branding).




Request

{
  "custom_branding": {
    "sender_email_address": "user@company.com"
  }
}




Response 200 — full GET shape; custom_branding.sender_email_address reflects sub-user override; sender_email_verified may be false until verified.

    }
  }
}
```
